What is a Multi-Agent System?

Flip each card to see the contrast. Click again to flip back.

Single Agent
🤖
One loop, many tools
One agent handles everything. Great for focused workflows like the VPN lab. Breaks when prompt/tool list grows too large.
flip to see where it fails
Failure Modes
✗ Prompt overloaded with conflicting roles
✗ Tool list too long → LLM picks wrong tool
✗ Can't parallelize research paths
✗ No clear owner of the final answer
flip back
Multi-Agent System
🤝
Several role-bound agents
Agents collaborate via messages, handoffs, or shared state. Each has a narrow role, scoped tools, and a clear output contract.
flip for the definition
Working Definition
A MAS is a set of agents that collaborate — via messages, handoffs, or shared state — to complete work that is hard for one overloaded agent.

Someone must own sequencing, stop rules, and the final answer.
flip back
Rule of thumb: Split into multiple agents when roles, tools, or success criteria diverge. If you can't name distinct specialists, stay single-agent.

Module 2

Why MAS? And When NOT to Use It

Understanding both sides prevents over-engineering. Flip the "When NOT" cards to reveal common traps.

✅ Why MAS
⛔ When NOT to Use
Specialization
🎯
Different skills per agent
Different prompts, different tool permissions, easier unit testing of each role. Mirrors how real teams work in Deloitte engagements.
Parallelism
⚡
Scale the work
Parallel research paths, stage pipelines, reuse specialists across flows, independent retries per role. Speed up broad scan tasks dramatically.
Risk Containment
🛡️
Narrower blast radius
Risky tools on one designated agent. Approver as a separate role. Clear escalation owner. Each agent only sees what it needs — no accidental privilege escalation.
Key insight: In regulated environments like Deloitte's audit and IT practices, risk containment is the primary driver for multi-agent architecture — not speed.
Trap 1
🔁
Simple tool loop
One clear workflow with few tools — adding agents just adds overhead with no benefit.
flip for decision rule
✓ Decision Rule
If you can describe the whole workflow in 3–4 tool calls with no role conflicts, stay single-agent. Example: VPN diagnosis with 6 tools is still single-agent territory.
Trap 2
🌫️
No clear roles
If you cannot name distinct specialists with different success criteria, you'll just get agents that chatter endlessly.
flip for decision rule
✓ Decision Rule
Can you write a separate system prompt for each agent that has zero overlap? If no → one agent. Name the roles before writing code.
Trap 3
⏱️
Hard latency / cost caps
Parallel crews multiply tokens and API wait time. Multi-agent can be 3–5× more expensive.
flip for decision rule
✓ Decision Rule
Profile single-agent first. Add parallelism only when you have a measured bottleneck. Premature parallelism = expensive bugs.
Trap 4
♾️
Missing stop rules
Without max turns / termination conditions, groups wander and rack up cost.
flip for fix
✓ Fix
Always define: max turns per agent, termination signal, and escalation path. In the lab: MAX_REVIEW_LOOPS=1, review decision is either approve or request_changes.
Trap 5
❓
Unowned final answer
If no single agent is responsible for assembling and signing off the result, the output quality degrades.
flip for fix
✓ Fix
Someone must be the output owner. In Bug Fix Crew: Reviewer owns the final decision. In hierarchical ITSM: Manager closes the ticket. Never leave it implicit.
Module 3

Architecture Building Blocks

Design these 4 dimensions before picking any framework. Click each block to expand.

Roles
Name each agent's job
The most important design decision. Each agent needs a name, one job, success criteria, and allowed tools only.
Role Design Checklist:

✓ Can you write a one-sentence job description?
✓ Can you name the tools each agent is allowed to use?
✓ What does a successful output look like for this role?
✓ Does any other agent overlap in responsibility?

Example: Planner → get_bug_report, list_repo_files only. Coder → read_file, propose_patch only. Reviewer → run_checks, submit_review only.
click to expand
Communication
How agents pass information
Handoff message, shared state object, group chat, or graph edges. The choice drives your framework selection.
Communication Modes:

📨 Handoff message — structured JSON passed explicitly (Bug Fix Crew)
🗄️ Shared state — LangGraph state dict that all nodes read/write
💬 Group chat — AutoGen's conversation model, speaker rules
🕸️ Graph edges — conditional routing in LangGraph

Rule: the tighter the contract, the more reliable the handoff.
click to expand
Control
Who starts, stops, approves
Orchestrator owns sequencing. Must define: who starts the crew, who approves risky actions, and what the stop conditions are.
Control Checklist:

✓ Entry point: which agent runs first?
✓ Sequencing: fixed order or dynamic routing?
✓ Stop conditions: max turns, termination signal
✓ Approval gates: which actions need human sign-off?
✓ Escalation path: what happens if a step fails?

In today's lab: Orchestrator pauses after each agent and waits for learner to type "okay" — explicit HITL between every phase.
click to expand
Observability
Trace, log, audit
Trace per agent, tool call logs, final audit trail. Often forgotten in demos — essential for enterprise sign-off.
Observability Requirements:

📊 Per-agent trace: what did each agent think and do?
🔧 Tool call log: every tool name, args, result, timestamp
📝 Final audit: structured record of the whole crew run
🗄️ Persistent storage: SQLite in lab, Jira/ADO in production

In today's lab: Every patch and review is written to SQLite. The faculty checklist asks you to run B1c (inspect DB) after each crew phase to see what was written.
click to expand

Module 5

Pattern Chooser

Answer 3 questions to get a recommended pattern for your use case.

Q1: Do the sub-tasks depend on each other's output?
Yes — each step needs the previous result
No — tasks can run independently
Q2: Is there a policy owner or approval gate above the specialists?
Yes — someone approves, routes, or escalates
No — agents are equal peers
Quick Reference
Sequential
Choose when…
✓ Stages depend on prior output
✓ You want simple audit trails
✓ Quality > raw speed
e.g. Research → Write → Review
Parallel
Choose when…
✓ Subtasks are independent
✓ Breadth scan then merge
✓ You can afford merge cost
e.g. News + Competitors + Pricing scan
Hierarchical
Choose when…
✓ Policy / approval sits above
✓ Many specialists, one owner
✓ Escalation paths matter
e.g. IT desk: Manager routes to specialist

Orchestrator & Handoff Contracts

The orchestrator owns policy. Handoff contracts create trust between agents. Flip cards to see good vs bad patterns.

🎯 Orchestrator Role
1
Owns the user goal
Receives the original request, keeps track of overall progress
2
Picks next agent / branch
Decides routing, enforces sequential or conditional logic
3
Enforces approvals & stops
Owns the HITL gate. Max turns. Escalation path.
4
Returns final answer
Assembles sub-agent results into a coherent output
Golden rule: Don't give every agent every tool. Only the orchestrator owns policy decisions.
Bad Handoff
❌ Free-text dump only
❌ Missing ids / evidence
❌ Hidden assumptions
❌ "Looks fine" with no proof
❌ Next agent re-does all work
flip for fix
✓ Fix
Use a schema + validator before the next agent runs. Every handoff must have: ticket_id, evidence fields, confidence level, and recommended next action.
Good Handoff
✓ Goal remnant (what still matters)
✓ Structured fields (ids, status)
✓ Evidence already obtained
✓ Confidence / unknowns stated
✓ Recommended next action
flip for example
Example JSON
"ticket_id": "INC-10422",
"user_id": "priya.n",
"finding": "vpn_disabled",
"confidence": 0.95,
"next": "reset_with_approval"

Frameworks for Multi-Agent Systems

Click a framework to explore its mental model, strengths, watch-outs, and code pattern.

👥 CrewAI

👥
CrewAI
Role-based crews. Agents + Tasks + Process. Business-friendly and fast to prototype.
Role-BasedSequentialHierarchicalFast Prototype
Mental model: Crew = team · Agent = role + goal + tools · Task = work unit · Process = sequential or hierarchical execution
Strengths
  • Fast role prototyping
  • Business-friendly language
  • Maps to real org job titles
  • Great for demos & POCs
  • Natural teaching surface
Watch-outs
  • Less graph-level control
  • State can feel opaque
  • Vague tasks → drift
  • Not ideal for hard approval gates
from crewai import Agent, Task, Crew researcher = Agent(role="Research Analyst", goal="Find root cause of BUG-1048", tools=[get_bug_report, list_repo_files]) coder = Agent(role="Software Engineer", goal="Fix the login button bug", tools=[read_file, propose_patch]) task1 = Task(description="Analyse BUG-1048", agent=researcher) task2 = Task(description="Propose a patch", agent=coder) Crew(agents=[researcher, coder], tasks=[task1, task2]).kickoff()
🕸️
LangGraph
Stateful agent graph. Nodes, edges, shared state, conditional routing, explicit loops.
StatefulCyclesHITLCheckpointsAudit
Mental model: Node = agent/tool/gate · Edge = transition · State = shared memory · Conditionals = routing · Human node = approval gate
Strengths
  • High observability
  • Regulated / audit flows
  • Approval & escalation paths
  • Deterministic stop rules
  • Best for enterprise control
Watch-outs
  • More design upfront
  • Steeper learning curve
  • You own the graph design
  • Overkill for simple demos
from langgraph.graph import StateGraph, END graph = StateGraph(CrewState) graph.add_node("planner", run_planner) graph.add_node("coder", run_coder) graph.add_node("reviewer", run_reviewer) graph.add_node("human_gate", hitl_pause) # HITL graph.add_edge("planner", "human_gate") graph.add_edge("human_gate", "coder") graph.add_conditional_edges("reviewer", route, {"request_changes": "coder", "approve": END})
🤖
AutoGen (Microsoft)
Group chat patterns. Agents converse with speaker selection rules and termination conditions.
Group ChatCode ExecDebateReview Loops
Mental model: Group chat with speaker selection policy · Optional human proxy · Debate / critique loops · Termination conditions required
Strengths
  • Natural multi-party talk
  • Great for review & critique cycles
  • Flexible experiments
  • Human can jump in any time
  • Built-in code execution
Watch-outs
  • Chatter burns tokens fast
  • Path less guaranteed
  • Needs max-turn caps always
  • Harder for strict compliance
  • Not first pick for approval gates

Module 8

Challenges & Mitigations

Click each challenge card to reveal the mitigation strategy.

Coordination
Who speaks next?
Without explicit sequencing, agents can run out of order, duplicate work, or deadlock waiting for each other.
Mitigations:

✓ Use an explicit orchestrator node/agent
✓ Define graph edges (LangGraph) or process (CrewAI)
✓ Set max consecutive auto-replies (AutoGen)
✓ Turn caps per agent (MAX_STEPS in today's lab)

In the Bug Fix Crew: CrewSession tracks waiting_for state and only advances when the learner types "okay".
click for mitigation
Trust
Can B rely on A's output?
If Agent A returns junk or a hallucination, Agent B will build on it without knowing — cascading errors are hard to debug.
Mitigations:

✓ Schema validate handoff messages before passing
✓ Require evidence fields (ids, source citations)
✓ Add a validator node between agents
✓ Fail fast at stage boundaries — don't silently continue

Example: run_checks in Block 4 validates the patch before Reviewer submits a decision. If no patch exists, it returns error immediately.
click for mitigation
Conflict
Contradictory outputs
Parallel agents may return conflicting findings. Who wins? Without a resolution strategy, the final answer is undefined.
Mitigations:

✓ Synthesizer agent with ranked source priority
✓ Human gate for unresolvable conflicts
✓ Explicit uncertainty field in handoff schema
✓ Never silently pick one — surface the conflict

Example (market scan): if Competitor says price is $X and News says price dropped — Synthesizer must mark uncertainty, not pick one silently.
click for mitigation
Cost & Latency
Agents multiply token usage
Each agent gets its own LLM calls. Parallel crews can be 3–5× more expensive than a single agent for the same task.
Mitigations:

✓ Profile single-agent first, then justify parallelism
✓ Cache intermediate results in shared state
✓ Use cheaper models for simple roles (e.g. gpt-4o-mini for Planner, gpt-4o only for Reviewer)
✓ Hard token budgets per agent

Block 4 uses gpt-4o-mini for all roles — lower cost for a lab context.
click for mitigation
Security Sprawl
Too many agents with too many tools
Each agent that can call a tool is a potential attack surface. More agents = larger blast radius if one is compromised.
Mitigations:

✓ Strict tool allow-lists per role (enforced in code)
✓ Secrets never in prompts — use env vars or vault
✓ Audit log every tool call with args and result
✓ HITL gate before any write/delete/reset action

Block 4: Planner only gets get_bug_report + list_repo_files. submit_review is exclusively Reviewer's tool. Enforced by the schemas_for() function.
click for mitigation
Chatter Loops
Agents talking without progress
Especially in group-chat frameworks, agents can debate endlessly without reaching a conclusion, burning tokens.
Mitigations:

✓ Always set max_round / MAX_REVIEW_LOOPS
✓ Require structured output (approve/request_changes — no freeform)
✓ Termination condition: final answer is a specific signal, not "looks done"
✓ In AutoGen: use termination keyword in system prompt

Block 4: MAX_REVIEW_LOOPS=1 ensures the crew terminates after at most one revision cycle, even if Reviewer keeps requesting changes.
click for mitigation

Click "Run Crew" above to watch the 3-agent simulation →
The root cause in useLoginState.ts:
setIsLocked(true); is called on failure but never cleared. Button stays disabled because const disabled = isSubmitting || isLocked; — once isLocked is true, no path resets it without a page refresh.
Why 3 Agents Instead of 1?
Tool Isolation
Planner has no write access. Coder can't approve. Reviewer can't write code. Each role is limited to exactly what it needs — zero chance of accidental cross-role action.
Independent Testing
You can unit test Planner's output without running Coder. You can swap a better Reviewer model without touching Planner logic. Roles are modular.
Real Org Mirror
This mirrors how real dev teams work: PM scopes, engineer codes, reviewer approves. The agent architecture maps directly to team responsibilities.
